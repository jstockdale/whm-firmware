# RAM audit + optimization, wave 1 (0.69.0)
## Trigger: BLE enable starved the chime (owner). Field numbers at
## 0.68.3, BLE off: post-wifi 96K free / min-ever 92K; post-bring-up
## 63K free, largest 28K. whlink boot-fuse latched from crash loops.

## FINDINGS
1. Internal STATICS are already lean: the largest .dram symbols are
   4.0K (lineedit history), 3.7K, 3.0K (port IntStack), 1.9K. No
   static whales to hunt.
2. mp3's "20480" is a FALLBACK line - the player task has been
   PSRAM-stacked (static create + PSRAM stk) all along. The audit's
   first lead was a mirage; the fallback was restored untouched.
3. NimBLE host memory: ALREADY external (PSRAM) in sdkconfig. The
   BLE-on internal delta is therefore controller heap + host/whlink
   task stacks (~35-50K) - exactly the margin the chime lost.
4. The movable middle (task stacks, internal today):
   dj_srv 4096, bf_pump 4096, bf_cli 4096, whm_sync_tx 4096,
   ssh 7168  ->  ~23K recoverable.
   Deliberately INTERNAL and staying: fleet_exec / wl_exec (flash-
   safe executors by design), whm_repl (direct NVS: ssh addkey),
   whm_ui (render hot path), audio trio (timing), wifi/sys.

## WAVE 1 (this release)
- The five stacks above -> xTaskCreatePinnedToCoreWithCaps(SPIRAM),
  each with its flash-safety rationale in-line. Forever-tasks, so
  the WithCaps delete rule is moot.
- ssh's move breaks with the watch's keep-internal caution ON
  PURPOSE: register-mode crypto never DMA-touches the stack, and
  the panels need the 7K more than the caution.
- Projection: post-bring-up free 63K -> ~86K; BLE-on lands
  ~40-50K free with the chime alive. Field verdict:
  flash, clean-boot 3x (clears the boot-fuse), then 'ble enable',
  then 'mem tasks' - internal min-ever is the number of record.
